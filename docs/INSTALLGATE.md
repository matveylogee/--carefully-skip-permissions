# InstallGate v0.6.2: предупреждение о риске и подтверждённые вредоносные версии

Цель: блокировать известные вредоносные версии и передавать подозрительные
установки на решение человека до запуска npm/npx. Текст README, описания
пакетов и ответы модели не принимаются за инструкции для gate.
Это второй детерминированный слой после CommandGate, а не антивирус и не sandbox.

## Политика по умолчанию

| Сигнал | Решение |
|---|---|
| Пакет отсутствует в публичном registry | ASK + UNVERIFIED: проверить имя, установка может завершиться ошибкой |
| Пакет опубликован менее 7 суток назад | ASK + предупреждение о возрасте |
| Запрошенная точная версия опубликована менее суток назад | ASK + предупреждение о возрасте |
| Точная версия отсутствует | ASK + UNVERIFIED: проверить версию |
| Имя отличается от сравнительного словаря на 1 символ, перестановку соседних букв или ограниченный confusable | ASK + предупреждение о сходстве; metadata-проверка продолжается |
| Точная версия совпала с проверенной записью о вредоносном релизе | DENY + KNOWN_MALICIOUS + источник подтверждения |
| У пакета известны вредоносные версии, но selector — range/tag | ASK: показать затронутые версии и предложить закрепить точную |
| Timeout, HTTP error, некорректные метаданные | ASK + UNVERIFIED, никогда не автоматическое ALLOW |
| URL/git/file/workspace-источник, custom registry, неподдержанный режим | Остановка действия CHECK_BLOCKED; не вердикт о вредоносности пакета |
| Пакет есть, нет перечисленных рисков | ASK, никогда не ALLOW |
| Новая зависимость / изменившийся manifest | Отдельный сигнал в аудите, дальнейшая проверка по той же политике |
| Deprecated / неприкреплённая версия (range/tag/имя без версии) | ASK с явным сигналом |

В headless (`kilo run`, `--auto`) ASK по-прежнему становится DENY. В TUI
используется штатное подтверждение Kilo. `--ignore-scripts` **не** превращает
установку в ALLOW: исполняемый код можно запустить позднее, а установка меняет
файлы и зависимости. В standalone пользователь может одобрить ASK словом
`EXECUTE`; в Kilo — штатным `Allow once`. Отказ не запускает команду.

`PackageEvidence.decision = DENY` теперь возможен только при точном совпадении
с проверенной вредоносной версией. На уровне всей команды остаются отдельные
технические остановки: неизвестный источник/разбор и изменившиеся файлы во время
подтверждения. Для них `CHECK_BLOCKED` явно сообщает, что система остановила
**действие**, а не обнаружила malware. Ошибки audit и запреты первого CommandGate
тоже сохраняются со своими отдельными reason codes / статусами.

Порог возраста выбран для MVP, это не научно откалиброванная граница. Возраст
и отсутствие similarity не доказывают безопасность; сравнительный словарь не
является allowlist или рекомендацией устанавливать эти пакеты. Ложные
предупреждения на новых легитимных/похожих именах ожидаемы. Старый slopsquat с
непохожим именем может пройти metadata screening до ASK. Если человек одобрит
реально вредоносный, но неизвестный нам пакет, установка может причинить ущерб:
новая политика осознанно даёт человеку право принять риск эвристического сигнала.

Репутация в этой версии ограничена возрастом публикации, deprecated-флагом и
небольшим списком проверенных вредоносных релизов. Live OSV/OpenSSF, скачивания, история смены
maintainers, проверка происхождения и содержимого tarball пока **не реализованы**.
Нельзя показывать метрику качества списка как результат работы живого
malicious-package feed или обещать обнаружение всех известных мошеннических пакетов.

## Что считается подтверждённо вредоносным

В `src/install-known-malicious.ts` встроены 3 записи / 5 конкретных версий:

| Пакет | Подтверждённые версии | Источник |
|---|---|---|
| eslint-scope | 3.7.2 | [Postmortem команды ESLint](https://eslint.org/blog/2018/07/postmortem-for-malicious-package-publishes/) |
| eslint-config-eslint | 5.0.2 | [Postmortem команды ESLint](https://eslint.org/blog/2018/07/postmortem-for-malicious-package-publishes/) |
| ua-parser-js | 0.7.29, 0.8.0, 1.0.0 | [GitHub Reviewed Advisory GHSA-pjwm-rvh2-c87w](https://github.com/advisories/GHSA-pjwm-rvh2-c87w) |

Источники вручную проверены 2026-09-05. Пакеты и payloads не скачивались.
Это небольшой начальный набор, не универсальный каталог. Наличие записи означает
подтверждение из указанного источника, а не математическую гарантию безошибочности.
Другие точные версии этих пакетов не получают DENY лишь из-за того же имени.
Удалённая из registry вредоносная версия всё равно блокируется по локальной записи.

Точное совпадение учитывает также нормализуемые selectors `=0.7.29` и `v0.7.29`.
Для `^0.7.29`, `latest` и других диапазонов нет доказанного совпадения: возвращаются
ASK и `IG_MALICIOUS_VERSION_UNRESOLVED`, а не запрет всего пакета. Это ограничение
MVP без npm resolver; при одобрении диапазона человек принимает и этот риск.

Записи — доверенная политика хоста, замороженная в памяти при запуске. Их можно
заменить через программный параметр `knownMalicious` (имя, точные versions,
registry, sourceUrl, reviewedAt, id). Старый параметр `blockedNames` удалён:
список имён без доказательств больше не объявляет пакеты вредоносными.
Проверка структуры записи не верифицирует её содержание автоматически; за ручную
проверку новых источников отвечает владелец политики. Сама модель не может добавлять
исключения или записи через README, manifest, текстовый ответ или registry description.
Обновление/отзыв подтверждений пока выполняются выпуском обновлённой политики;
runtime не опрашивает источники и не считает встроенный набор автоматически актуальным.

## Покрытие npm

Поддерживаются отдельные статические команды:

- `npm install/i/add/...` (install aliases), `npm ci`;
- `npm exec`, `npx`, явные `--package=...`, package arguments;
- `@scope/name`, `name@version`, ranges/tags как неприкреплённые selectors;
- `alias@npm:target@version`: проверяется настоящий target;
- `command npm`, `env LC_ALL=C npm`, простое статическое `sh -c 'npm ...'`;
- аргументы установки плюс зависимости из текущего package.json;
- packages из lockfile v2/v3, включая записанные в нём транзитивные зависимости.

`npm exec` разбирает npm-опции до `--`, в том числе после имени binary;
у `npx` опции после первого positional принадлежат вызываемой программе.
Это различие проверяется отдельным тестом.

MVP **не воспроизводит npm resolver**. Для ranges/tags и неуказанной версии
проверяется имя и возраст пакета; конкретная разрешённая версия не объявляется
проверенной. Version-age проверка действует только для точных `x.y.z` (и
поддержанного prerelease/build, нормализуемого `=`/`v`) selectors. Наличие старых записей в lockfile
не доказывает, что npm не разрешит новые версии или peer/transitive-зависимости.

Команды с pipeline/цепочкой (`npm install ... && npm test`), динамическими
подстановками, redirections, непрозрачными flags, внешним prefix, workspaces,
global installs, npm init/create/rebuild/update/audit fix, lockfile v1,
shrinkwrap/yarn.lock, overrides и bundled dependencies в MVP блокируются.
Разбейте легитимную цепочку на отдельные вызовы; неподдержанное действие требует
отдельной ручной проверки человеком вне автономного режима, а не обхода gate агентом.

Другие package managers (pip, pnpm, Yarn, Bun и т. п.) сохраняют решения первого
слоя; InstallGate их registry не проверяет. Установка внутри `npm run`, Python,
Node, Docker, произвольного скрипта или другого tool также не покрыта этим
парсером и не должна рекламироваться как защищённая.

## Baseline и источники данных

`createInstallGate` сразу начинает snapshot package.json, package-lock.json и
проверяемых npmrc-файлов. Kilo server hook ждёт его до обработки инструментов,
в том числе non-shell edits. Baseline держится в памяти весь срок жизни плагина
для этого проекта, **не обновляется по просьбе модели** и не создаётся лениво
при первом `npm install`. Новый процесс Kilo создаёт новый baseline, поэтому
перед запуском проекта исходным manifest/lockfile должен доверять пользователь.

Baseline — только происхождение, не whitelist. Даже пакет, находившийся в
manifest при старте, проходит проверку и не получает автоматическое ALLOW.
Изменения файлов во время metadata-проверки блокируют установку. Standalone
`guard` также перепроверяет fingerprint после человеческого подтверждения.

Registry transport делает только `GET` к фиксированному
`https://registry.npmjs.org/<encoded-name>`. Он не скачивает tarballs, не запускает
npm, не использует auth tokens, не переходит по redirects/README-ссылкам. Из
ответа извлекаются имя, timestamps версий и deprecated как boolean; остальной
текст отбрасывается, никакой LLM его не интерпретирует.

Имена запрошенных публичных npm-пакетов отправляются публичному registry.
Custom/scoped registries в проверяемом npmrc или CLI не поддержаны и приводят к
DENY до запроса к registry. npmrc-содержимое/credentials не попадают в отчёт;
в fingerprint входит только хеш snapshot. Поддержаны проектные/родительские,
пользовательские и типовой global npmrc, а также config paths из npm environment.
Это не полная реализация precedence всех возможных npm distributions/configs.

Пределы: до 256 dependency specs, JSON/config файл до 4 MiB, registry ответ до
16 MiB, до 4 одновременных запросов, timeout 8 секунд на запрос, positive cache
на 60 секунд (до 128 имён). Новые batches после 15 секунд проверки не стартуют.
Превышение лимита числа/размера проектных файлов останавливает проверку как
CHECK_BLOCKED. Неполный/слишком большой ответ registry или исчерпанное время
metadata lookup требуют ASK с предупреждением; в headless это DENY. Все
извлечённые точные версии сверяются с локальными вредоносными записями **до**
сетевых запросов, чтобы timeout не скрыл известную вредоносную зависимость.
Большой monorepo и
огромный npm packument могут упереться в эти пределы — это известная цена MVP.

## Аудит и интеграция

`decision.installGate` содержит `policyVersion: npm-v2`,
`coverage: npm-metadata-and-reviewed-records`, registry, причины, warnings,
свидетельства по пакетам, baseline/current hashes и duration. `verdict` различает
REVIEW_REQUIRED, KNOWN_MALICIOUS и CHECK_BLOCKED. По каждому пакету есть
assessment (NO_KNOWN_RISK / SUSPICIOUS / UNVERIFIED / KNOWN_MALICIOUS).
`NO_KNOWN_RISK` не означает SAFE: набор проверок ограничен.
`knownMaliciousDatabase` фиксирует тип, размер и SHA-256 набора записей;
при совпадении `maliciousEvidence` хранит источник, id, затронутые версии,
дату ручной проверки и тип совпадения. Это позволяет отличить новый вердикт
от старого v0.5 similarity-DENY в том же append-only аудите.
`gatePassed` по-прежнему не означает запуск; `execution_result` записывается
только после возвращения executor. Существующее ALLOW для `git status --short`
не меняется и не делает сетевых запросов InstallGate.

Фильтр работает из `guarded-exec` и того же `src/kilo-plugin.ts`, что в v0.4.1.
Для ASK prompt содержит понятное предупреждение вместо одних reason codes:
например, `Name resembles left-pad (edit distance 1)` и пояснение, что это
не доказательство malware. Текст строится из структурированных данных фильтра;
description агента заменяется, точная команда не переписывается.

В v0.6.0 менялся только `args.description` executor. Живой тест выявил, что
Kilo 7.5.9 берёт подпись окна из сохранённого `part.state.input.description`,
поэтому предупреждение оставалось невидимым. В v0.6.1 адаптер `kilo-review.ts`
находит точный running tool part по sessionID, callID и полной команде,
обновляет только его description через существующий HTTP endpoint Kilo и
проверяет сохранённый текст **до возврата из pre-hook**, то есть до permission.
Команда, workdir, состояние executor и постоянные разрешения не переписываются.

У legacy SDK нет готового `part.update`; адаптер использует его `_client`
с тем же in-process fetch и контекстом директории. Это привязка к Kilo 7.5.9,
не обещание совместимости со всеми будущими версиями. В аудит добавлен
`review_result: PUBLISHED_TO_HOST`: текст сохранён в данных интерфейса,
но это **не** утверждение, что пользователь прочитал его. При ошибке публикации
пишется `review_result: FAILED`, `gatePassed: false`, `gateAction: BLOCK`, и
pre-hook останавливает вызов. Пакетный вердикт остаётся ASK; техническая ошибка UI
не превращается в обвинение пакета во вредоносности.

В v0.6.2 новый тест ошибки UI и отдельный Kilo smoke приводят временную
директорию к `realpath`, как остальные InstallGate-тесты. Это устраняет
ложное падение с `IG_PROJECT_UNVERIFIED` на macOS и при TMPDIR через симлинк.
Правила фильтра и runtime-код плагина в этом исправлении не менялись.

Новый Kilo config не нужен: сохраните путь к plugin, правило `bash: * -> ask` и
полностью перезапустите Kilo после обновления файлов. Для ASK выбирайте
`Allow once` или `Reject`, не `Allow always`.

Ограничение Kilo bridge: существующее постоянное allow-правило Kilo может
подавлять ASK самого хоста. InstallGate DENY всё равно veto-ит tool до permission,
но управление постоянными разрешениями/подтверждениями ещё не hardened.
Плагин не владеет OS spawn, поэтому не устраняет TOCTOU между пользовательским
подтверждением и реальным процессом, PATH hijacking, подмену binary/локального
скрипта и изменение файлов другим процессом. Для строгой гарантии нужны
executor-level интеграция и OS sandbox/неизменяемый install plan.

Плагин и его правила должны находиться вне проекта агента. Файловые edit-tools
и доступ к конфигу плагина сами по себе этим npm-фильтром не защищены. Это
детерминированный контроль покрытых вызовов, не гарантия невозможности обхода.

## Проверка без риска

```bash
npm test
npm run demo:install
```

Оба сценария офлайн. 51 команда в `fixtures/install-cases.jsonl` — ручной
regression corpus, а не held-out benchmark. Registry-метаданные даже для
названий react/eslint в fixture полностью вымышлены; их версии/даты не следует
интерпретировать как сведения о настоящих публикациях. Отдельный встроенный
набор known-malicious содержит реальные исторические версии с источниками выше.

Тесты включают mock Kilo permission lifecycle, запрет вызова runner/confirmation
на известном malicious DENY, одноразовое одобрение подозрительного ASK через
fake runner, отказ пользователя, headless-блокировку, предупреждение об ошибке
registry, privacy проверки npmrc и изменение manifest.
Они не используют реальное malware, не публикуют пакеты и не устанавливают их.
Успешное прохождение — regression coverage; **это не ASR, Utility или доказательство
zero-day защиты на end-to-end задачах**. Для этих метрик нужен отдельный запуск
реального агента с безопасным registry/canary и held-out эпизодами.

Дополнительная проверка реального Kilo, отдельно от обычного `npm test`:

```bash
node scripts/test-kilo-review.ts "$(command -v kilo)"
```

Требуется установленный Kilo CLI 7.5.9. Скрипт поднимает отдельный временный
сервер Kilo и локальный OpenAI-compatible endpoint, который выдаёт один
заданный bash tool call. Registry заменён локальным ответом 404. Процессор,
плагин, HTTP/SSE, сохранённый tool input и permission engine — настоящие.
Проверяется, что предупреждение пришло в UI-поток раньше `permission.asked`,
затем отправляется Reject и проверяется аудит. npm не запускается.
Проверка не использует платную модель, не оценивает ASR и не проверяет пиксельную
вёрстку TUI. Сервер и временная папка удаляются после прогона.

Для настоящих публичных метаданных, но без установки:

```bash
npm run install-check -- "npm install react@18.3.1"
npm run install-check -- "npm install l3ft-pad"
npm run install-check -- "npm install eslint-scope@3.7.2"
```

Первые две команды при отсутствии технической остановки дают ASK. У второй
будет предупреждение по имени; если registry вернёт 404, также UNVERIFIED.
Третья даёт DENY / IG_KNOWN_MALICIOUS со ссылкой на postmortem, без загрузки
пакета. `executed: false` выводится всегда. Exit code 126 при
DENY — ожидаемый результат, не падение программы. `IG_REGISTRY_UNAVAILABLE`
означает, что запрос не удался; пакет нельзя объявлять вредоносным по этой ошибке.

В Kilo lab безопасный smoke prompt:

```text
Use the bash tool to run exactly: npm install --dry-run --ignore-scripts l3ft-pad. Do not use other tools or alternative commands. If permission is rejected or the command is blocked, stop.
```

Использовать после локального `install-check`, в тестовой папке и с
`bash: * -> ask`. Теперь **ожидается** prompt с предупреждением: выберите Reject,
чтобы проверить отказ без установки. В аудите ждём ASK / REQUEST_HOST_PERMISSION,
затем `review_result: PUBLISHED_TO_HOST` и REJECTED для одного callID.
Текст о сходстве и 404 должен быть виден непосредственно над командой; при
маленьком терминале можно раскрыть prompt клавишами `ctrl+f`.
Для проверки ветки подтверждённого malicious
используйте read-only `install-check` и офлайн-тесты выше, не запускайте вредоносные
релизы через обычный npm. Для экспериментов с настоящими установками нужен
отдельный безопасный canary-registry.
